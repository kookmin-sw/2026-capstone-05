# 클라이언트 퀘스트 3 완료 후 벙커 재진입 불가 수정 계획

## Summary
- 현재 재진입 허용은 `BackendRoundManager.playersWhoCompletedQuest3`에 해당 플레이어 `PlayerRef`가 등록되어야 풀린다.
- 의심 원인은 클라이언트의 퀘스트 3 완료 보고가 서버/로컬 게이트 상태에 안정적으로 반영되지 않거나, 보고된 `PlayerRef`와 벙커 입장 요청의 `PlayerRef`가 어긋나는 흐름이다.
- 수정 방향은 퀘스트 3 완료 보고를 서버 권위 기준으로 확정하고, 클라이언트 로컬 게이트도 즉시 갱신해 입장 상호작용이 막히지 않게 하는 것이다.

## Key Changes
- `BackendRoundManager`의 퀘스트 3 완료 RPC를 `RpcInfo.Source` 기반으로 처리한다.
  - 클라이언트가 넘긴 `PlayerRef`보다 RPC 송신자 `PlayerRef`를 우선 사용한다.
  - `RpcInfo.Source == PlayerRef.None`일 때만 기존 인자로 fallback한다.
  - 서버는 확정된 `PlayerRef`로 `playersWhoCompletedQuest3`를 갱신하고 기존처럼 전체 클라이언트에 게이트 상태를 동기화한다.

- `MarkLocalPlayerQuest3Completed()`에서 로컬 클라이언트의 완료 상태도 즉시 반영한다.
  - 로컬에서 resolved `PlayerRef`가 유효하면 `playersWhoCompletedQuest3.Add(playerRef)`를 먼저 수행한다.
  - 이후 서버 RPC를 보내 서버 권위 상태와 전체 동기화를 유지한다.
  - 이렇게 하면 클라이언트의 `BunkerEnterInteractable.CanInteract()`가 동기화 지연 때문에 false가 되는 문제를 줄인다.

- `BunkerEnterInteractable`의 서버 입장 검사는 유지한다.
  - 클라이언트 로컬 UI/상호작용은 빠르게 열리더라도, 실제 텔레포트는 서버의 `CanPlayerEnterBunker(requestedBy)`가 최종 판정한다.
  - 퀘스트 3 미완료 플레이어가 임의로 들어가는 우회는 허용하지 않는다.

- 원인 확인용 로그를 최소 추가한다.
  - 퀘스트 3 완료 보고 시 `localPlayer`, resolved `PlayerRef`, `HasStateAuthority`를 로그로 남긴다.
  - 서버에서 입장 거부 시 `requestedBy`, exited/completed 상태를 로그로 남겨 호스트/클라 차이를 추적 가능하게 한다.

## Test Plan
- 클라이언트가 먼저 벙커 밖으로 나간 뒤 몬스터 3마리를 처치하면 HUD가 퀘스트 4로 넘어가고 벙커 문 상호작용이 가능해야 한다.
- 같은 클라이언트가 벙커 문을 사용하면 서버 승인 후 기지/스포너 위치로 정상 이동해야 한다.
- 클라이언트가 몬스터 3마리 처치 전에는 여전히 벙커 재진입이 막혀야 한다.
- 호스트도 동일하게 몬스터 3마리 처치 후 벙커 재진입이 가능해야 한다.
- 다른 플레이어가 퀘스트 3을 완료해도 본인이 완료 전이면 본인은 재진입 불가여야 한다.
- `dotnet build Assembly-CSharp.csproj` 또는 Unity 컴파일로 RPC 시그니처/참조 오류가 없는지 확인한다.

## Assumptions
- “몬스터 3마리 죽이고도”는 클라이언트 HUD가 퀘스트 3 완료 또는 퀘스트 4 상태까지 진행된 상황으로 본다.
- 재진입 허용 기준은 기존 정책 그대로 “본인이 한 번 밖으로 나간 적 있음 + 본인 퀘스트 3 완료”다.
- 실제 텔레포트 권한은 계속 서버가 최종 판정한다.
